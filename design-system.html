Ink & Grid

Complete light-only reference for the deploy portal: principles, tokens, component gallery, and usage rules. Stack: Hono SSR HTML, one plain CSS file (vibeship.css), tiny vanilla JS — no build step. Accent: signal orange #e85d04. Example data only — not live from the VM.

Companion files: vibeship.css (tokens and rules) · src/ui/components.ts (the components that render them)

Principles

Six rules that keep Ink & Grid consistent across the portal. Every page builds from the components in src/ui/components.ts, so following them is the default.

PrincipleMeaning
FlatNo drop shadows. Depth comes from ink borders and the cream page / white surface split.
Two border weights--border-strong (2px ink) only on the primary container of a page section: a table, a form card, a dialog, the login card. Everything nested inside (stat cards, chips, tags, inputs) uses --border-thin (1px). No other weights.
Orange is not a statusOrange is only for the brand, primary buttons, links, the active nav item, the active tab and the selected filter. Statuses use four tones: success, warning, danger, neutral.
Mono for machine valuesHostnames, image refs, digests, ports, uid:gid, IPs, URLs, IDs, JSON: --font-mono, usually with a copy button. Words are serif (--font-ui), including inputs holding words.
Names over IDsShow a token's name, a user's email, a project's name, linked where a page exists. The raw reference (token:2) goes in the tooltip.
Ask before destroyingStop, Revoke, Remove and Delete are danger buttons behind the confirm dialog.

Color usage

Do

  • Orange fill for the one primary action per view (Deploy, New project).
  • Orange for links, the active nav item, the active tab and the selected filter chip.
  • A tone for every status, from the mapping below.
  • Red for failed and for destructive actions only.

Don’t

  • Use orange for a status, a live indicator or a meter.
  • Make a scope red: admin is warning, never danger.
  • Write hex literals in templates or rules; use the tokens.
  • Put white text on #e85d04.

Do

  • Use .label for every field label, card label and table header.
  • Use mono for the same kind of value everywhere, inputs included (a port is mono in every form).
  • Keep page padding on the spacing scale.

Don’t

  • Mix arbitrary radii (e.g. 8px or 12px) outside the tokens.
  • Give nested elements the strong border.
  • Remove focus outlines without replacing --focus-ring.

App shell

When to use. Every signed-in page: cream top bar and icon sidebar, content centred on the cream page. Breadcrumbs sit left-aligned next to the logo; the user menu holds the email and Log out.

Do

  • Every sidebar icon has an aria-label and a tooltip; the MCP button carries a caption.
  • Breadcrumb labels match page and tab names (Settings, not settings).
  • Title, description and the primary action in pageHeader().

Don’t

  • Put primary actions in the sidebar.
  • Repeat the filter chips' counts as stat cards.

Buttons

When to use. Primary (orange) for the one main action per view; secondary (outline) for alternatives; danger for every destructive action, always behind the confirm dialog; ghost for quiet chrome like Cancel.

Do

  • Set a destructive action apart (.action-sep) from Deploy and Restart.
  • Primary label is ink on orange (AA).
  • Icon-only buttons have an aria-label.

Don’t

  • Two primaries in one header.
  • A destructive action without postButton(…, { destructive }).

Inputs

When to use. field(): label, input, optional help, inline error. Forms are novalidate; ui.js checks required, min/max and pattern and writes the message under the field instead of a browser bubble. Form fields sit on a 4-column grid so edges line up row to row.

Do

  • .input-mono / .textarea-code for machine values; numbers are mono by default.
  • Help text says what an empty field means.
  • Secrets are password inputs with a show/hide button.

Don’t

  • Placeholder-only labels, or placeholders as dark as values.
  • Red borders without an error message.

Status badges & tags

When to use. statusBadge() for every status: a dot and a tone, rounded. tag() for a kind (image/compose), a token scope or an audit action: neutral rounded-rect, mono.

Do

  • Always include the status word, never colour alone.
  • Admin scope may use the warning tone.
  • Danger tone on a tag only for destructive audit actions.

Don’t

  • Orange for any status.
  • A red scope tag.

Data table

When to use. Project lists, deploy history, tokens, the audit log. dataTable() wraps it in the strong border; headers use the label role; actions sit in a right-aligned column whose header only screen readers see.

Do

  • Machine values in mono with a copy button where useful; digests as tag + 7 characters.
  • Hostnames link out with the external-link icon.
  • Relative times; absolute UTC in the tooltip.

Don’t

  • Zebra stripes or drop shadows.
  • A raw ID (token:2) as a cell's label.

Info list & tabs

When to use. A key/value list in a card for a project's details: keys in the label role, machine values mono, plain-language values serif. Tabs switch the sections of a project.

Do

  • Show a value once: the hostname lives in the page header, not also in the list.
  • Say what an empty value means ("No health path, healthy while the container runs").

Don’t

  • Nested strong-bordered cards.
  • Lowercase breadcrumb or tab names.

Deploy log & timeline

When to use. Live or historical deploy output; timeline for step progress beside the stream.

Do

  • Mono body, line numbers, .log-ok / .log-err stream colors.
  • Live: .log-live + pulsing dot; aria-live="polite" on the stream.

Don’t

  • Colored backgrounds per line (keep stream colors on text).
  • Hiding timestamps — operators need them.

Alerts, toast, modal

When to use. Inline alerts for page-level outcomes; toasts for brief confirmations; modal for destructive confirms.

Do

  • Danger confirms use .btn-danger and name the resource.
  • Dialog: role="dialog" aria-modal="true", Escape closes, focus trap in product.
  • Toasts: aria-live="polite".

Don’t

  • Auto-deleting a project without a confirm dialog.
  • Stacking many toasts that block the page.

Env rows & API token (shown once)

When to use. Env vars are a data table with a Remove action; the shown-once box appears right after creating a token or a webhook URL.

Do

  • Mask secrets; never re-display a token.
  • Shown-once: a warning badge, the label, the mono value, a Copy button.

Don’t

  • Log the raw token anywhere, including the audit log.
  • Show secret values in plain text by default.

Code, pagination, skeleton, avatar

When to use. Inline/code blocks for commands; pagination for long lists; skeletons while loading; avatar in the user chip.

Do

  • Inline code for paths and short commands; .pre-block for multi-line payloads.
  • Skeletons match content width, not random bars.

Don’t

  • Emoji avatars in product UI.
  • Pagination without a current-page indicator.

Accessibility

Contrast, focus, keyboard, and ARIA expectations for every interactive pattern.

AreaRequirement
ContrastBody, muted and subtle text meet AA on cream and on white. Accent text uses --accent-text (5.0:1 on cream). On-accent uses ink (5.4:1). Every status tone meets AA on its tint.
FocusAll interactive elements show --focus-ring via :focus-visible. Never remove outlines without a replacement.
TabsProject tabs are links; the current one has aria-current="page".
DialogsNative <dialog> opened with showModal(): labelled title, Escape dismisses, focus moves in. The confirm dialog focuses Cancel first.
Togglesrole="switch" + aria-checked; space/enter toggles.
Toastsaria-live="polite" on the stack.
ColorDon’t rely on color alone: status badges include a word (Running), not only a dot.
Icon buttonsEvery icon-only button has an aria-label; sidebar icons also have a tooltip.
FormsErrors are text under the field, linked with aria-describedby and aria-invalid.

UI writing style

Sentence case, short labels, precise errors — no marketing tone.

Do

  • Sentence case: New project, not New Project.
  • Short verbs: Deploy, Rollback, Logs.
  • Relative times in tables (12m ago); absolute on hover (2026-11-03 11:50:00 UTC), the same format everywhere.
  • Errors say what failed and what we did: Health check failed. Previous digest restored.
  • Destructive confirms name the resource: Delete project notes?

Don’t

  • Marketing tone or emoji in product UI.
  • Title Case On Every Button.
  • Vague errors (Something went wrong) with no next step.

Adding a new component

Keep the system closed: tokens first, then classes, then this page.

  1. Prefer composing existing tokens and primitives (.card, .btn, .mono).
  2. Add classes to vibeship.css under a clear section comment — no one-off hex literals in templates.
  3. Primary containers get --border-strong + --radius-md; anything nested gets --border-thin.
  4. Document the component here with realistic Vibeship copy, When to use, and Do / Don’t.
  5. Render it from a helper in src/ui/components.ts, so pages can’t drift from the rules.
  6. Keep JS optional and tiny; progressive enhancement only (tabs, toggle, modal, dropdown, copy, SSE log tail).

Stack reminder. Hono + hono/html templates render these class names. Serve or inline vibeship.css — no bundler.
